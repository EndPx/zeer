# Four Zcash services: historical transaction lookup and normalization

Measured on 2026-10-13. **All four candidates passed the same finite serving task.** This is a native-path transaction lookup benchmark, not a fresh-ingestion or engine-speed ranking.

## Workload and oracle

- 128 transactions selected at deterministic heights `1 + floor(i*2047/127)` from mainnet blocks 1–2048. Prefer the first non-coinbase v1 transaction at each selected height; otherwise use its v1 coinbase.
- Actual composition: **78 coinbase, 50 non-coinbase; all pre-Overwinter v1**. No Sapling/Orchard/decryption coverage.
- Frozen source: Zakura v1.5.0, mainnet height **6764**, hash `0000000160e11c9403141d7c2a16b07a2459919fc774795da3f687628c5ece54`.
- Expected fields come from decoded source RPC and archived block membership. Raw transaction identity is separately checked with SHA256d. The timed decoder does not generate expected counts/locktime.
- Seven shared fields: txid, mined height, version, locktime, serialized byte size, transparent input count including coinbase input, and transparent output count.
- One reused connection, 128 sequential per-ID requests per run; one fully verified warmup followed by five runs. Verification and source-anchor checks are outside the serving timer.

## Results

**Times below are totals for 128 sequential lookups, not single-request latency.**

| Candidate | Native read path | Passed runs | Median total | Min–max |
| --- | --- | ---: | ---: | ---: |
| lightwalletd v0.5.5 | gRPC raw bytes + client v1 decode | 5/5 | 300.719 ms | 207.087–319.756 ms |
| Zaino 0.10.1 | gRPC raw bytes + client v1 decode | 5/5 | 2153.367 ms | 2003.823–2466.542 ms |
| Zinder v0.6.0 | gRPC raw bytes + client v1 decode | 5/5 | 141.719 ms | 105.091–206.319 ms |
| CipherScan / zecblock-rust 15d7f528 | Indexed PostgreSQL fields | 5/5 | 29.142 ms | 25.776–47.725 ms |

Every timed run matched every expected record and field in the frozen order. Preflight, warmup and postflight passed. No aggregate sample was selected from failures. All four reports share the same manifest and benchmark-code hashes.

CipherScan has already parsed and stored the requested fields; its timed adapter reads those columns. The gRPC adapters obtain serialized transactions and decode on the client. These are equivalent requested outputs but different backend work. The SQL result must not be advertised as faster transaction decoding, faster index construction, or an overall engine win. The ordering also differs from the earlier compact-block experiment, demonstrating workload dependence.

## Resource profile and order

- Shared Hostinger VPS: four logical CPUs, about 16 GiB RAM; other applications remained running.
- User-authorized expanded envelope: **3 aggregate vCPU, 8GiB RAM, 40GiB operational disk**. No hosting-plan purchase/upgrade.
- Measured serving allocation: source 1 CPU / 2 GiB, candidate 1 CPU / 4 GiB, client 1 CPU / 512 MiB. CipherScan serving candidate is its PostgreSQL process after backfill exits. Zinder groups four unmodified native services in one 1 CPU / 4 GiB cgroup.
- Candidate order: CipherScan, Zinder, lightwalletd, Zaino. This is one ordered session, not randomized independent sessions; retain that limitation.
- Cache state: verified full-workload warmup, without OS-cache isolation. Timing includes transport, Python/gRPC or psycopg processing, thread dispatch and normalization.
- Client/protocol deps: Python 3.12 image pinned by digest, grpcio/grpcio-tools 1.84.0, protobuf 7.36.2, psycopg/psycopg-binary 3.3.6.
- No per-sample provider CPU/peak-RAM trace was captured. Saved Docker configuration documents limits, not actual resource consumption.

## How the previous exclusions were resolved

### CipherScan

The original regtest dataset was incompatible with its network support. This experiment uses actual mainnet state and the exact source-aligned **Zakura 1.5.0 state v29**. The tested binary comes from successful upstream CI run 38329349273 at commit 15d7f528f07a84d796ed89029de21bfb26a24d23, artifact 11782029111. Binary SHA256: `67932d9a4a2cf545ddeefefa785a007cc925b09884b8f18b703cb89598b2a735`. No candidate source logic was patched.

Its unmodified backfill indexed 6,764 blocks and 64,620 transactions into a separate PostgreSQL database. It reported 457.7 seconds during preparation. That is a setup observation under preparation quotas, **not a comparable four-way ingestion result**. Its query baseline begins only after backfill completed.

### Zinder

The official v0.6.0 native archive was checksum-verified. Four unmodified release processes ran in custom benchmark packaging, with bounded RocksDB/sorter settings and a combined 4 GiB memory ceiling. This proves that this small dataset ran with that configuration; it does not establish a general minimum RAM requirement.

The first serving attempt refused readiness because a frozen prefix is behind current mainnet. Ingest/projector had completed, but query reported `upstream_not_ready`. That was preserved as a setup finding rather than bypassed with fabricated RPC responses.

The source node was then configured with its **actual health endpoint** and an explicit historical-fixture policy: min_connected_peers = 0, ready_max_blocks_behind = 4,000,000, ready_max_tip_age = 2h. Zinder points to that actual `/ready` endpoint and retains strict fallback settings. The real endpoint returned HTTP 200 (`ok`); all four Zinder services then passed their genuine readiness checks. RPC verification progress remained approximately 0.0019; nobody claimed current-mainnet synchronization.

This relaxed historical health policy is part of the benchmark configuration and must be disclosed. It is unsuitable as evidence that a production node is current. No mock health responder, fake peer count, false synchronization progress or patched Zinder guard was used.

### Frozen source and bootstrap correction

The initial bootstrap omitted the image-specific CONFIG_FILE_PATH variable, so the intended 2048 stop was not loaded. The node was manually stopped at 6764 while its state was only a few hundred MB. This setup error is why the actual frozen head differs from the planned selection range.

The serving restart used the explicit CONFIG_FILE_PATH, no peer seeds/cache, and an internal no-egress Docker network. All candidates refer to this same unchanged head. Do not combine this dataset with the earlier synthetic regtest fixture.

## Operational outcome and remaining limits

All benchmark containers were stopped. Previously checked application services stayed active. The new experiment directory occupied 2,923,575,431 bytes (about 2.73 GiB), with additional pinned images; total incremental usage remained far below 40 GiB. No global Docker cleanup, unrelated service restart, billing change, or application-database mutation occurred.

This establishes a common task supported by all four measured deployments. It does not cover modern shielded transaction formats, wallet decryption, private memos, GraphQL, throughput at scale, or Zeer engine performance. Next comparisons should preserve distinct serving, decoding, scanning and durable-ingestion tracks.
