# Zeer Chef public-data MVP and first indexing benchmark

Executed 14 October 2026, Asia/Jakarta. Chef now has a local unpublished package,
TypeScript handlers and generated types, explicit PostgreSQL namespace setup,
ordered block processing, durable checkpoints/undo, and authenticated read-only
GraphQL. Prep's implementation was held at its existing MVP.

## Benchmark definitions

The user's Envio references distinguish two jobs:

- **Chef/application indexing:** source reads, handlers and committed application
  entities. Count transactions only after their block transaction commits and
  verify the resulting database. The guide recommends fixed historical ranges,
  fresh databases and profiling where time is spent.
  [HyperIndex benchmarking](https://docs.envio.dev/docs/HyperIndex/benchmarking).
- **Prep/data retrieval:** full scans, sparse public matches and selected fields,
  timed until equivalent data is received/decoded. Zcash workloads use public
  transaction IDs, transparent outputs and public pool structures; EVM logs,
  private recipients and plaintext memos are not assumed.
  [HyperSync overview](https://docs.envio.dev/docs/HyperSync/overview).

The main table below is application indexing. The prepared transaction lookup
against lightwalletd is explicitly a separate supplemental serving test.

## Same application workload, two data sources

Each repetition began with a new empty, fingerprinted PostgreSQL namespace and
processed **heights 1–2048 inclusive**, containing **16,962 transactions**. This
is an early-mainnet public range containing legacy v1 and v2 transactions.
It is not genesis-inclusive and does not represent a modern shielded workload.

The identical TypeScript example writes one `PublicTransaction` entity with seven
public fields, creates one `Block` entity per block, and reads/updates that block's
transaction counter in every transaction handler. Every block commits its entity
changes, before-images and checkpoint atomically. Each successful repetition
produced **19,010 verified entities**: 2,048 blocks and 16,962 transactions.

| Pipeline | Fresh repetitions | Median indexing seconds | Committed transactions/s | Min–max seconds |
| --- | ---: | ---: | ---: | ---: |
| Chef + Prep | 5 | **55.715** | **304.441** | 51.033–59.640 |
| Chef + full-node RPC benchmark adapter | 5 | **60.187** | **281.823** | 51.141–66.568 |

Primary timing starts at the first source request after namespace initialization
and ends after the last PostgreSQL entity/checkpoint commit. Node synchronization,
Prep archive construction, configuration import/schema setup, oracle collection,
result verification and GraphQL validation are excluded and recorded separately.
The runner also records ingestion-to-verified-GraphQL duration, including the
post-ingestion verification work; do not substitute that for primary indexing time.

Every persisted entity was checked after reopening the store, using an independent
full-node oracle. Raw legacy transaction IDs were checked by double SHA-256;
v1 raw locktime was checked at its tail, while v2 decoded locktime came from the
node because JoinSplit data follows it. All ten runs passed entity, checkpoint,
count, source-anchor and real GraphQL response verification.

The two modes use the same schema, handlers, page size 16 and PostgreSQL commit
semantics. The RPC adapter uses sequential `getblockhash`/`getblock` requests with
one in flight, no source cache and exact JSON numeric-token preservation. It is
a benchmark adapter for this frozen range, not a production alternative source.
Prep was already prepared before timing, as were the node's validated blocks.

All Prep repetitions preceded all RPC repetitions. Both used warm sources on a
shared VPS with fresh application namespaces. Timing ranges overlap, so the
observed median difference is not a statistically established universal speedup.
This compares **Chef with two data sources**, not two independent application
indexing frameworks.

## Native CipherScan ingestion, different output workload

The pinned unmodified [CipherScan Rust indexer](https://github.com/Kenbak/cipherscan-rust/tree/15d7f528f07a84d796ed89029de21bfb26a24d23)
also completed five fresh-database backfills over the same **1–2048** range.
All **2,048 blocks and 16,962 seven-field transaction projections**, plus the
native checkpoint at 2048, matched the same independent oracle in every run.

| Native pipeline | Fresh repetitions | Median process seconds | Verified committed transactions/s | Min–max seconds |
| --- | ---: | ---: | ---: | ---: |
| CipherScan + read-only RocksDB secondary + PostgreSQL | 5 | **21.821** | **777.317** | 19.800–28.959 |

CipherScan was faster in these observed runs. The workloads and allocations differ,
so this is not a controlled pure-framework ranking or universal speedup claim.
It reads prepared node state directly and writes its native explorer schema:
in addition to the common blocks/transactions, each run stored 15,622 input rows,
60,061 output rows, 20,596 address rows and 71,975 address-transaction rows.
These additional rows were counted; their complete semantics were not independently
verified. Chef's example instead uses generic JSONB entities, TypeScript handlers,
per-block counter updates and an undo journal. This experiment does not establish
equivalent recovery semantics between the two products.

Native timing begins before container creation and ends after native process exit,
including startup and RocksDB secondary opening. Schema setup and verification
are excluded and timed separately. Both node synchronization and primary RocksDB
preparation are excluded. The source node remained stopped and its state was
mounted read-only; each run used separate writable secondary/spool storage.

The native profile used 1.75 CPU / 4 GiB for CipherScan, 1 CPU / 2 GiB for its
isolated PostgreSQL, and 0.25 CPU / 512 MiB for the controller: 3 CPU / 6.5 GiB
aggregate. This differs from Chef's allocation above. PostgreSQL durability
settings remained on. Docker samples are retained; precise native process CPU
and peak RSS were not measured. Native database size includes database catalogs
and the full explorer schema, so it must not be ranked against Chef's namespace-only
storage size.

An initial five-run series also passed (median 26.952 s). Review then found and
fixed a cancellation race before container creation. A deliberate one-second
timeout returned `NATIVE_BACKFILL_TIMEOUT` and left its container stopped, allowing
Docker's shutdown grace period. The final five runs above use the corrected
runner with its own SHA-256 and immutable runtime image ID. Both series and the
timeout attempt are retained; only final-series values enter the table.

## Where time went

| Median phase, seconds | Chef + Prep | Chef + RPC |
| --- | ---: | ---: |
| Source requests, including returned-data decoding | 1.971 | 7.967 |
| Handlers, including entity database I/O | 43.696 | 41.881 |
| Remaining transaction work | 9.741 | 10.354 |

Phase medians need not add to the median elapsed time. Transaction overhead means
`store.apply` time minus awaited handlers: begin, identity checks, journal,
checkpoint, pruning and commit. It is **not isolated COMMIT latency**. Handler
time is **not pure JavaScript CPU** because entity reads/writes are awaited there.

This baseline points toward entity access and persistence as the next profiling
priority. The current implementation makes per-entity SQL calls and one durable
commit per block; it does not have a batch/preload cache. No optimization or
performance superiority is inferred solely from Envio's events/s thresholds.

The measured Node process peaked at about 338 MiB sampled RSS for Prep mode and
330 MiB for RPC mode. That process also retains oracle/verification structures,
and all repetitions reuse it. These are harness-process observations, not isolated
Chef heap requirements. Per-run CPU deltas, sampled RSS and process-lifetime
maximum RSS are retained; GC/event-loop metrics were not measured.

## Supplemental external-provider lookup

The existing 128 distinct v1 transaction manifest was rerun against the preserved
Chef projection and **actual lightwalletd v0.5.5**, both backed by the same frozen
canonical source. One verified warmup preceded five measured reads per candidate.

| Prepared serving path | Median for 128 verified records |
| --- | ---: |
| Chef GraphQL + PostgreSQL | 520.849 ms |
| lightwalletd gRPC + client normalization | 193.851 ms |

All seven output fields matched the independent manifest. The APIs perform
different work: Chef authenticates, executes GraphQL and reads a transactional
database snapshot; lightwalletd supplies raw transaction bytes, decoded by the
client. Source/archive/application preparation is excluded. This does **not** rank
Chef's indexing engine against lightwalletd. An external application-framework
indexing comparison still requires equivalent durable schemas and handler work;
an explorer's larger native tables are not assumed equivalent.

## Whole-chain request

The fresh [preflight](../../../docs/CHEF_BENCHMARK_PREFLIGHT.md) observed public
mainnet tip **3,516,619** with agreeing height/hash across the inspected providers.
Provider coverage differed: one compact endpoint rejected height 0, another served
it, and compact transaction counts differed for the same tip block. A compact
entry count cannot silently replace all-public-transaction counts.

The current local source is frozen at **6764**, and Prep's archive/import contract
starts at 1. The observed CipherScan node state was **282,311,217,721 bytes**, about
263 GiB. The experiment allows 40 GiB additional disk and the shared host had about
80 GiB free. That observed footprint is not a claimed minimum for every possible
architecture, but the current full-node/full-archive path cannot fit it.

**Genesis-to-tip was not run. Its duration is null.** No small-range extrapolation
is presented as a measured whole-chain result. A complete run requires a source
and storage plan with complete public coverage, plus explicit genesis support.

## Correctness, CLI and review

The actual PostgreSQL test run passed **31 Chef tests, zero skipped**, including
atomic handler failure, restart without duplicate handlers, bounded application
undo/replay, source-unavailability/read gates, exact BigInts, project/writer
isolation, real GraphQL readiness responses, authentication and query bounds.
Runtime reorg tests use deterministic source branches with real PostgreSQL;
they do not claim a new actual-node Chef reorg test.

The CLI was separately exercised through explicit `migrate`, `sync --to 8`, an
idempotent second `sync`, and `serve`. The second sync committed zero additional
blocks/transactions. Its real HTTP 200 GraphQL response matched eight transactions
from the independent oracle. Generated types passed positive/negative tests and
the example's explicit TypeScript type check. Six RPC-adapter tests and seven
lookup-adapter tests also passed.

Independent review found two issues before the final run: source unavailability
could leave a prior checkpoint readable, and a PostgreSQL readiness rejection
could return 500 instead of 503. Both were fixed and covered by regression tests.
The initial whole-range oracle also assumed every transaction was v1; the wider
range revealed v2 transactions. It was corrected without weakening identity or
entity checks. Those failed/setup attempts are retained separately from results.
