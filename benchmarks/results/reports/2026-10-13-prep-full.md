# Zeer Prep full-data prototype

Executed 2026-10-13. **Complete blocks/transactions, multi-segment ingestion,
query API, typed client and bounded source following are implemented.** This is
a bounded functional prototype, not universal HyperSync parity or a public
production deployment.

## Real mainnet-range correctness

The source is the previously validated and frozen Zakura 1.5.0 mainnet prefix
at height 6764, hash
`0000000160e11c9403141d7c2a16b07a2459919fc774795da3f687628c5ece54`.
The complete source image digest is in [execution evidence](../raw/2026-10-13-prep-full/execution.json).
It is intentionally not synchronized to the current public tip.

| Check | Observed result |
| --- | --- |
| Selected range | Mainnet 1000–2023 inclusive |
| Complete serialized blocks | 1,024 |
| Complete transactions | 13,817 |
| Archive layout | Eight segments of 128 blocks |
| Restart continuation | Stop after height 1255, restart and reach 2023; no duplicate segment publication |
| Full API verification | All raw blocks, decoded block objects, raw transactions, vin/vout and decoded transaction objects equal independent node reads |
| Exact numeric values | Node JSON decimals/integers preserved; nested decoded values exposed as strings |
| Transaction-ID filter | Expected transaction returned and other transactions excluded |
| Transparent-output address filter | All 1,024 matching transactions equal the independent expected set |
| Client installation | Local npm pack installed into a separate consumer directory; no registry publication |
| Actual SDK consumption | 16 pages, 1,024 blocks, 13,817 transactions; full decoded-block number handling checked |

The importer verifies serialized header identity, parent/time, transaction
count and exact transaction-byte inclusion. It does not independently verify
consensus, proofs, Merkle roots or modern transaction-ID algorithms. The node
is the authority for those checks and for decoded field meaning. This mainnet
range contains early pre-Overwinter transactions; it is not modern-shielded
production coverage.

## Narrow serving comparison

Task: retrieve **height, block hash and timestamp for the same 1,024 blocks**.
Both candidates have already prepared their state. Prep uses its checked header
index; the node uses `getblock(hash, 1)` with known block hashes. This compares
native read paths with equivalent final fields, not identical backend work.

| Tool | Data path | Headers/s | Median total | vs fastest | Verification |
| --- | --- | ---: | ---: | ---: | --- |
| Zeer Prep, release build | Prepared header index; HTTP pages of 128 blocks | 125,806.3 | 8.139 ms | Fastest | 5/5 |
| Zakura 1.5.0 full node | JSON-RPC; 8 workers with reused connections | 1,758.9 | 582.184 ms | 71.5× slower | 5/5 |

These times cover the **entire 1,024-header task**, not one block's latency.
Prep's sample range was 7.386–16.788 ms; the node's was 534.798–1041.588 ms.
One warmup preceded five runs, with candidate order alternating. Full equality
checks followed each timer. The Python RPC helper preserves JSON decimals,
whereas the selected final header fields are integer/string values; native
response size and client normalization differ and are included in the timing.

All runs used the same shared host. Source and Prep each had one CPU; the client
had one CPU. Limits are not consumption traces. No cold-cache isolation,
dedicated-host stability, arbitrary-concurrency saturation or million-block
experiment was performed. **71.5× applies only to this prepared-header task.**
It is not a full-block, transaction-ingestion, decryption or general indexer
speedup. It cannot be combined with earlier compact/transaction benchmarks.

An earlier development implementation read full payloads even for header-only
queries. Its retained observation was 343.780 ms for Prep versus 536.413 ms for
the node. That result predates the checked header index and is preserved as
development history, not the published leaderboard's candidate build. A first
indexed run observed 8.690/598.258 ms; the final verification also added a real
transparent-output filter check and produced the table above. All raw runs are
retained rather than selecting individual favorable repetitions.

## Following, reorg and failure evidence

An isolated copy of the original Zebra 6.2.3 Regtest fixture began at height
1024. Prep caught up from 1020 and followed two newly generated local blocks:

- Source and indexed head reached **1026**, with observed lag zero.
- The two new complete blocks and their two **version-6 transactions** were
  retrievable; raw block bytes matched the actual node.
- An existing pagination cursor retained its old captured end while new
  requests could read the appended blocks.
- Mining occurred only on the disposable isolated copy. The original fixture
  and existing application data were not changed.

Reorg recovery, source shortening, deep-reorg refusal and forks during capture
were tested with controlled HTTP node fixtures. Real-node growth is observed;
a real-node reorg and sustained public-network follow were not demonstrated.
Structural test transactions are not consensus-valid chain evidence.

Setup corrections are retained: initial source startup preceded RPC readiness
and failed cleanly, then resumed; the private Regtest node required empty peer
seeds to avoid blocked DNS startup. Zebra's Regtest RPC reports `chain: test`;
the adapter now resolves that ambiguity using its exact known genesis hash,
verified against upstream's serialized genesis fixture, with regression tests.

## Validation and operational outcome

- **64 Rust tests passed:** archive/storage, full source/follower, query/HTTP and
  retained compact integration tests.
- **13 Node SDK tests passed**, including pagination, cancellation, exact-number
  handling, typed reorg errors and actual local HTTP interaction.
- Strict TypeScript consumer check passed with TypeScript 7.0.2; runtime checks
  used Node 24.18.0. A packed package was tested against the private VPS service
  over a temporary local SSH tunnel, which was closed afterward.
- Formatting, Clippy with `-D warnings`, and optimized release build passed on
  Linux x86_64 / Rust 1.99.0. Cargo.lock fixes the dependency resolution.
- Independent review led to response-buffer permit ownership, coherent status
  checks, cursor boundary anchoring and same-epoch archive-prefix checks.

All owned experiment containers stopped and the five previously checked
application services remained active. No Prep port was publicly published.
Build/ingestion/serving phases stayed within the authorized aggregate 3 CPU /
8 GiB / 40 GiB envelope. The full-data experiment directory occupied about
150 MB; all Prep work directories including shared build caches occupied about
1.85 GB, with additional pinned images. No paid upgrade or unrelated cleanup
occurred.
