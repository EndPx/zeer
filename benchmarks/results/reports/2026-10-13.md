# Initial Zcash provider benchmark — 2026-10-13

**Measured scope: frozen synthetic regtest compact-block serving and normalized header verification.** No Zeer engine, application persistence, nonempty shielded transactions, decryption, or GraphQL is measured.

## Environment and fixture

- Shared Hostinger KVM VPS: 4 logical CPUs, AMD EPYC 9354P, approximately 16 GiB RAM. Other services stayed running. CPU quotas are not dedicated cores.
- Zebra 6.2.3, lightwalletd v0.5.5 and Zaino 0.10.1 are pinned by image digest in the source/catalog and run evidence. Zaino OCI revision matches its release source commit; its gRPC gitCommit field is empty.
- Regtest heights 1–1024, one transparent coinbase per block, zero shielded actions. The candidate projection therefore has zero shielded transaction IDs.
- Exact block bytes, RPC-derived expected records and checksums are committed in `benchmarks/fixtures/regtest-1024/`. A fresh isolated Zebra node successfully replayed all 1,024 archived blocks to the same tip.
- One full-range verified warmup precedes five measured reads. The timing includes client gRPC decode and normalization, and excludes independent verification.
- Both providers emitted 80,769 protobuf bytes per measured range (403,845 across five reads). Header/projection equality passes; full payload fields beyond the declared projection are not independently verified.

## Balanced CPU profile

Source: 0.25 CPU / 1,280 MiB; one provider: 0.75 CPU / 2,560 MiB; client: 1 CPU / 256 MiB. Aggregate ceiling: 2 CPU and 4,096 MiB. Run order in this profile: Zaino, then lightwalletd.

| Provider | Passed reads | Median read + normalize | Min–max | Blocks/s from median |
| --- | ---: | ---: | ---: | ---: |
| Lightwalletd v0.5.5 | 5/5 | 193.229 ms | 113.977–310.704 ms | 5299.4 |
| Zaino 0.10.1 | 5/5 | 105.724 ms | 73.298–123.679 ms | 9685.6 |

All ten measured reads in this profile returned exactly the expected 1,024 ordered records, with zero missing heights, duplicate heights, unexpected heights, or mismatched normalized fields. Client cgroup peak memory was about 32 MiB; this is client memory, not provider peak memory. Provider CPU and memory quotas were captured, but peak provider resource usage is not claimed.

Zaino had the lower observed median in this small profile. This does **not** establish a general speedup or ranking: the fixture is sparse, samples are short, the client participates in timing, caches are not independently isolated, and the VPS is shared.

## Original constrained-client profile

The first successful measurements used source 0.5 CPU, provider 1.25 CPU and client 0.25 CPU, with the same memory caps. Client cgroup counters showed heavy throttling. This motivated the separately declared balanced profile before those runs; the original results remain available and are not pooled with the second profile.

| Provider | Median | Min–max |
| --- | ---: | ---: |
| Lightwalletd v0.5.5 | 1200.169 ms | 501.159–1390.443 ms |
| Zaino 0.10.1 | 416.116 ms | 407.377–886.994 ms |

Order for this first profile: lightwalletd, then Zaino. Both passed all five reads. The large change after shifting the client quota is a reason to avoid attributing the original durations solely to provider performance.

## Compatibility findings and unsuccessful setup attempt

- `lightwalletd-round1-warmup.json` preserves a failed preflight: lightwalletd rejects `GetBlock(0)` with `INVALID_ARGUMENT`. No timed comparison was run on that attempt.
- The common preflight was corrected to verify block 1 and its parent genesis hash. It uses the same check for both providers.
- `GetBlock` can include transparent-only envelopes; the declared shielded projection excludes entries without shielded spends/outputs/actions. Nonempty transaction-ID normalization is unit-tested, not exercised by this live fixture.
- A native gRPC deadline is translated to TIMEOUT and aborts later repetitions. Warmup and measured result files remain separate.

## Other candidates

- **Zinder v0.6.0:** deferred resource-fit validation. Its upstream example allocates aggregate 6 GiB serving-process ceilings before Zebra. This is not proof of minimum RAM and not a failed performance result.
- **CipherScan:** requires a compatible direct-state/public-chain workload and PostgreSQL. The inspected network parser does not support regtest; it was not modified to force inclusion in this experiment.

## Operational outcome

All benchmark containers were stopped after the runs and replay verification. No existing application or database was stopped or reconfigured. Post-run checks found the previously observed application services active. The isolated runtime directory occupied approximately 41 MB; the sum of the four requested image size fields was approximately 253 MB (a conservative accounting component, not a full disk quota implementation). Usage stayed far below the 10 GiB operational budget. State and image caches were retained for inspection; no global Docker pruning was performed.

## Remaining work

This smoke baseline establishes a usable harness and successful execution of two real services. It is not completion of the broader benchmark specification. Add nonempty shielded datasets with independent truth, longer/dense workloads, index construction and persistence cases, controlled restart/reorg tests, and eventually the Zeer implementation as a participant.
